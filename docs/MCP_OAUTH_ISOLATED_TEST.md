# Geïsoleerde Supabase OAuth/MCP-proef — voorbereiding, NIET uitgevoerd

Status 27 september 2026: **productie UIT; geen echte issuer-test uitgevoerd**. De officiële [OAuth-flow](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows) beschrijft een access-JWT met `aud: "authenticated"` en top-level `client_id`, maar noemt `resource` niet bij de authorization-parameters. [Supabase Auth #2610](https://github.com/supabase/auth/issues/2610) vraagt nog openlijk om RFC 8707 (`resource` → `aud`); [#2820](https://github.com/supabase/auth/issues/2820) meldt een 400 bij de consent-detailaanvraag zodra `resource` wordt opgegeven (naast afzonderlijke problemen met public clients en `offline_access`). Dit zijn documentatie en meldingen van derden, **geen meting van een Lerno-testproject**. Onder deze omstandigheden is het nu niet verantwoord te beweren dat Supabase een aan Lerno's resource gebonden token kan leveren. Een token dat alleen dankzij een hook op `client_id` de juiste `aud` heeft, telt **niet** als issuer-enforced binding aan de daadwerkelijk aangevraagde resource.

## 0. Afbakening en harde stop

- Richt _eerst_ een **eigen wegwerp-Supabase-project** in, plus een aparte backend en frontend; eigen testgebruikers en sleutels, geen gedeelde database, OAuth-app, credentials, domein of sessies met productie. Breng de bestaande migraties inclusief `database/migrations/0006_profiles_role_privileges.sql` alleen dáár aan. Staging `SUPABASE_URL`/anon key/service-role key uitsluitend in de testservices volgens de bestaande deploymentdocumentatie. Niet in het script of dit document bewaren.
- Backend `PUBLIC_BACKEND_URL` = **exact de HTTPS-origin** waar de geïsoleerde backend extern bereikbaar is, zonder afsluitende `/`. Frontend `FRONTEND_URL` en zijn build-time `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` wijzen uitsluitend naar test. Auth **Site URL** = die testfrontend-origin; Auth **Authorization Path** = `/oauth/consent` (controleer dat de testfrontend deze route werkelijk serveert). Nooit productie-instellingen of connectors aanraken.
- Supabase-dashboard **Authentication → OAuth Server**: alleen in dat testproject inschakelen; vraag desnoods asymmetrische RS256/ES256 signing aan vóór `openid`. Voor de minimale proef gebruikt het script uitsluitend scope `email` en vraagt het geen ID-token. Test de normale login en consent-flow eerst handmatig op de geïsoleerde frontend. Gebruik korte access-token-TTL (bijvoorbeeld ≤ 5 minuten voor de verlopen-tokenproef) en refresh-rotatie volgens je testbeleid.
- Dashboard **Authentication → OAuth Apps**: registreer één aparte **public** OAuth-client (`token_endpoint_auth_method: none`, **geen client secret**) met uitsluitend de exact geregistreerde redirect `http://127.0.0.1:53921/callback`. Zet Dynamic OAuth Apps uit tenzij een afzonderlijke latere test daarvan nodig is. Supabase-documentatie vereist exacte redirectmatches. Als hosted Supabase deze loopback-redirect of de public-client-consent niet ondersteunt, noteer de blokkade en stop; verander de productieclient niet. Het script moet op **dezelfde lokale computer als de browser** draaien; `127.0.0.1` in een externe browser of Arena-preview verwijst niet naar deze sandbox.
- Maak disposable accounts **A**, **B** en, voor admincontrole, een **echte testadmin**. Controleer dat alle drie uitsluitend in de testdatabase bestaan en A/B verschillende Supabase `sub`/profiel-ID's hebben. Geef de testadmin alleen in test de `admin`-profielrol. Staging-wijzigingen pas doen nadat de afzonderlijke omgeving expliciet aangezet en geïdentificeerd is.
- Geen globale of cliëntspecifieke custom access-token hook voor `aud`, geen tweede auth-server, shared secret of kunstmatige claims. Als de issuer `resource` weigert/negeert of `aud` op `authenticated` laat staan: **stop de positieve proef**, blijf MCP in Supabase-modus fail-closed (401).

## 1. Exacte parameters

De operationele staging-host/project-ref zijn **nog onbekend**. Er is dus géén eerlijke concrete hostnaam om nu in te vullen. Stel voor de geïsoleerde omgeving `LERNO_TEST_BACKEND_ORIGIN` in op **dezelfde** origin als staging `PUBLIC_BACKEND_URL` en controleer `GET <origin>/.well-known/oauth-protected-resource/api/mcp`:

| Parameter                                                     | Exacte waarde voor het gekozen testproject                                                                                                                     |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MCP-resource (`resource` bij authorize **én** token exchange) | `${LERNO_TEST_BACKEND_ORIGIN}/api/mcp` = het `resource`-veld van de staging protected-resource metadata; geen `/` achteraan                                    |
| Protected-resource metadata                                   | `${LERNO_TEST_BACKEND_ORIGIN}/.well-known/oauth-protected-resource/api/mcp`                                                                                    |
| Issuer                                                        | `${LERNO_TEST_SUPABASE_ORIGIN}/auth/v1` (controleer AS-discovery)                                                                                              |
| Authorization endpoint                                        | `${LERNO_TEST_SUPABASE_ORIGIN}/auth/v1/oauth/authorize`                                                                                                        |
| Token endpoint                                                | `${LERNO_TEST_SUPABASE_ORIGIN}/auth/v1/oauth/token`                                                                                                            |
| Redirect URI van de testclient                                | **`http://127.0.0.1:53921/callback`**                                                                                                                          |
| Minimale proefscope                                           | `email` (géén `offline_access`; dat is een aparte compatibiliteitsvraag); `openid profile email` alleen na RS256/ES256-configuratie en een afzonderlijke proef |
| Public client                                                 | `client_id` van uitsluitend de test-OAuth-app, token endpoint auth `none`                                                                                      |

Geen `authenticated` als gevraagde resource, geen backend-origin zónder `/api/mcp`, en geen ID-token verwarren met het **access**-token: een ID-token heeft `aud = client_id` en is niet voor de MCP-resource bestemd. Ook `aud: [resource, "authenticated"]` voldoet **niet** aan Lerno's strikte singleton-resourcecheck.

## 2. Lokaal diagnostisch script (alleen na expliciete activatie)

Node ≥ 20, geen extra dependencies. **Geen netwerk bij** `--help` en `--prepare`. Voor `--run` moeten alle originwaarden expliciet worden gezet én handmatig als testomgeving bevestigd. Het script blokkeert een bekende productie-backendhost en checkt de metadata, maar kan **niet zelf bewijzen** dat een onbekende Supabase-project-ref of host geen productie is; de uitvoerder moet dat onafhankelijk verifiëren. Gebruik geen secrets in shell history, environment of argumenten; alleen public `client_id` en test-origins. Het script print nooit access/refresh-token, authorization code, state of PKCE-verifier. De lokale `/start` geeft de browser een 302 naar de issuer; de issuer en browser zien daarbij normaal de OAuth-parameters. Draai niet met HTTP-debug/proxy/body-logging.

```sh
export LERNO_TEST_BACKEND_ORIGIN='https://<afzonderlijke-test-backend-origin>'
export LERNO_TEST_FRONTEND_ORIGIN='https://<afzonderlijke-test-frontend-origin>'
export LERNO_TEST_SUPABASE_ORIGIN='https://<afzonderlijke-test-project-ref>.supabase.co'
export LERNO_TEST_CLIENT_ID='<client-id-uit-uitsluitend-testproject>'
export LERNO_TEST_USER_A_ID='<uuid-van-testgebruiker-A>'
# Optioneel voor --second-user en --admin-user:
# export LERNO_TEST_USER_B_ID='<uuid-van-testgebruiker-B>'
# export LERNO_TEST_USER_ADMIN_ID='<uuid-van-testadmin>'
node scripts/oauth-isolated-probe.mjs --prepare
# ALLEEN nadat testomgevingen actief en onafhankelijk geïdentificeerd zijn:
export LERNO_TEST_CONFIRM_ISOLATED=YES_ISOLATED_TEST_ONLY
node scripts/oauth-isolated-probe.mjs --run resource
```

Alle `--run`-varianten vereisen `LERNO_TEST_USER_A_ID` (testgebruiker UUID), zodat dezelfde gebruiker bij resource/no-resource/other-resource aantoonbaar wordt gebruikt; voor B en admin hun eigen verwachte UUID's. De `--run resource`-flow controleert eerst resource- en issuer-metadata; genereert cryptografisch willekeurige `state` en PKCE-verifier; stuurt `code_challenge = BASE64URL(SHA256(verifier))` en `code_challenge_method=S256` met `resource` naar authorize; wacht op de _exacte_ loopback-callback; verifieert state met een constante-tijdvergelijking; wisselt de single-use code binnen vijf minuten in via form-urlencoded POST met `grant_type=authorization_code`, dezelfde `client_id`, dezelfde `redirect_uri`, `code_verifier` en dezelfde `resource`. Geen confidential client-authenticatie. De lokaal gedecodeerde JWT-claims (`iss`, `sub`, `aud`, top-level `client_id`, `exp`) zijn **alleen diagnostiek**: Lerno moet dezelfde Bearer server-side met Supabase `getUser` valideren, `sub` vergelijken, en daarna de audience-check afdwingen. Een 200 op `POST /api/mcp` met `tools/list` is pas positieve evidence als de issuer het **exacte** `aud` gaf en de resource server werkelijk de token accepteerde. Bij een ontbrekende of afwijkende resource-`aud` stopt `--run resource` **vóór** een MCP-request; uitsluitend de aparte `no-resource`/`other-resource`-modi sturen hun negatieve controletoken naar MCP voor de 401-proef. Een 400 bij consent/token exchange, of `aud: authenticated`, is een blokkerende uitkomst, **geen** gedeeltelijk succes.

`--run` is expres opt-in; het script bevat geen server-side token signing, JWT-fabricage of OAuth-omweg. Het is een **voorbereide probe**, niet een reeds bewezen werkende Supabase-integratie. `--run` kan 5 minuten op de callback wachten; bij consent-400 in de testfrontend: noteer status/fase (zonder URL/tokens/codes) en breek de lokale probe af.

## 4. Beslissing vóór ooit een productie-activatie

De actuele documentatie plus open issues maken de **200-rij niet aantoonbaar haalbaar** met de gedocumenteerde Supabase OAuth-server; de lokale Lerno-fixtures in `backend/src/mcp-resource.test.ts` bewijzen alleen Lerno's fail-closed gedrag, niet Supabase-uitgifte. Een geïsoleerde _diagnose_ is zinvol zodra een eigen testproject bestaat, maar niet als een reeds werkende end-to-end-releaseproef presenteren. Vereist voor doorgaan: Supabase Auth voegt echte RFC 8707 resource-ondersteuning toe (**authorize, code, token endpoint, refresh**) en geeft een ondertekend access-token met exact resource-audience uit dat `getUser` én de bestaande RLS accepteren; óf de gekozen authorization-serverarchitectuur moet expliciet worden vervangen door een issuer/token-exchange die dit wel afdwingt, met een eigen securityreview van REST-/websiteauth en RLS. Een `client_id`-hook die `aud` vastzet, of het accepteren van `authenticated` in MCP, lost dit niet op.
